> 本章为 2026 年增补章节。AI 辅助编程已经从"新鲜玩具"变成日常工具，但它的**能力边界**和**正确用法**，比工具本身更值得花时间理解。本章讲清楚三件事：能用来干什么、什么时候别用、怎么把它的产出管住。

## 一、先建立正确预期

### AI 擅长什么

| 类型 | 说明 | 典型场景 |
|---|---|---|
| **样板代码** | 结构固定、模式重复 | CRUD 页面、表格表单、路由配置、类型定义 |
| **转换类** | 输入输出明确 | JS → TS、Vue 2 → Vue 3、Class → Hooks、正则解释 |
| **边界查询** | 有标准答案 | "这个 CSS 属性兼容性如何"、"这段报错什么意思" |
| **单点函数** | 输入输出清晰、无外部依赖 | 日期格式化、数组去重、节流防抖、深拷贝 |
| **解释代码** | 你给它读 | 接手陌生代码、看懂压缩后的产物 |
| **测试用例** | 覆盖面枚举 | 给已有函数补边界用例 |

### AI 不擅长什么

| 类型 | 原因 | 后果 |
|---|---|---|
| **跨文件的架构设计** | 上下文有限，看不到全局 | 局部合理、整体割裂 |
| **业务规则的隐含约束** | 你的项目有未写进代码的约定 | 写出"能跑但违反业务"的代码 |
| **性能关键路径** | 无法运行、无法 profiling | 看似优化、实则更慢 |
| **安全敏感逻辑** | 不承担后果 | 鉴权漏洞、注入风险 |
| **最新的 API 细节** | 训练数据有截止时间 | 用到已废弃 API 或用错签名 |
| **大规模重构** | 无法保证一致性 | 改一半、留下不一致 |

**一句话记住**：**AI 是打字速度，不是判断力。**它负责生成候选，你负责决定对错。

## 二、上下文比提示词重要

大多数人用不好 AI，问题不在 prompt 写得不够花哨，而在**给的信息不够**。

### 1. 给足项目上下文

```
❌ 差
帮我写一个用户列表组件

✅ 好
项目：Vue 3 + TypeScript + Vite + Pinia
UI 库：Element Plus
数据层：TanStack Query（不是 Vue Query），已有 api/user.ts 导出 fetchUsers()
约定：所有接口请求走 @/api，组件用 <script setup lang="ts">
要求：用户列表，支持分页、搜索、删除二次确认，
      表格列：姓名/邮箱/角色/创建时间，
      空状态用 ElEmpty，加载用骨架屏
```

**关键信息清单**（提问前对着过一遍）：

- 技术栈与**版本**
- 目录结构与命名约定
- 已有的工具函数、API 封装（避免重复造轮子）
- 代码风格（`ref` 还是 `reactive`、是否用 `any`）
- 明确的验收标准

### 2. 把相关文件贴进去

现代编辑器（Cursor、Copilot、Claude Code 等）支持 `@文件` 引用。**主动引用而不是指望它猜**：

```
参考 @src/api/user.ts 的写法，在 @src/views/UserList.vue 里实现列表页
```

### 3. 一次性给全类型定义

```ts
// 有类型，AI 才不会瞎猜字段名
interface User {
  id: string;
  name: string;
  email: string;
  role: 'admin' | 'editor' | 'viewer';
  createdAt: string;  // ISO 8601
}
```

## 三、几种高效用法

### 1. 类型先行

先让 AI 生成 TS 类型，人工确认后再生成实现。**类型是合同**，合同对了实现才有意义。

```
根据以下接口响应，生成 TypeScript 类型定义。
注意：role 只有三种值；deletedAt 可能为 null；metadata 是任意 JSON。
{...响应 JSON...}
```

### 2. 小步生成，逐步验证

```
❌ 一次性："帮我做一个完整的后台管理系统"
✅ 分步：
  1. 先给路由与页面骨架，我来确认结构
  2. 再逐个页面实现，每个页面单独验证
  3. 最后补状态管理与接口联调
```

每一步都跑一遍、看一眼。**AI 的错误会累积**，越晚发现越贵。

### 3. 让它当审查者，而不是作者

这是被低估的用法——**你已经写完的代码，让它挑毛病**：

```
审查这段代码，重点看：
- 是否有内存泄漏（定时器/监听器未清理）
- 是否有竞态（异步请求未取消）
- 是否违反 React Hooks 规则 / Vue 响应式陷阱
- 可访问性问题（aria、键盘操作）
按严重程度排序，只列问题不要重写。
```

它挑出来的问题里通常 30% 有价值，比自己 review 更容易发现盲区。

### 4. 让它写测试

```
给 @src/utils/format.ts 里的 formatDate 写 Vitest 用例，
必须覆盖：闰年、月末、时区、非法输入、空值。
```

测试是**验证 AI 是否真理解需求**的最快方式。

### 5. 让它解释而不是生成

面对陌生代码，读比写更花时间：

```
逐行解释这段代码的执行顺序，标出所有副作用，并告诉我哪里可能抛异常。
```

## 四、必须人工把关的地方

以下场景，AI 产出**必须逐行审**：

| 场景 | 风险 |
|---|---|
| **鉴权与权限判断** | 写反条件 → 越权 |
| **支付/金额计算** | 浮点数精度、四舍五入规则 |
| **密码与密钥处理** | 硬编码密钥、可逆加密冒充哈希 |
| **SQL / 查询拼接** | 注入 |
| **`innerHTML` / `v-html`** | XSS |
| **`eval` / `new Function`** | 代码注入 |
| **文件上传与路径拼接** | 路径穿越 |
| **正则表达式** | ReDoS、边界错误 |
| **并发与锁** | 竞态、死锁 |
| **数据迁移脚本** | 不可回滚的破坏性操作 |

**实际教训**：AI 生成的鉴权代码最常见的问题是**"看起来对"**——if 条件齐全、函数名正确，但判断逻辑反了或漏了 `else` 分支。这类 bug 通读一遍往往发现不了，**必须写测试**。

## 五、AI 出错的典型模式

认识这些模式，review 时能快速定位：

### 1. 幻觉 API

```ts
// ❌ Vue 里没有这个
import { useRoute } from 'vue-router';
const params = useRoute().value.params;   // useRoute() 不返回 Ref

// ❌ React 里 use 的用法混淆
const data = use(fetchData());            // 需要 Suspense 边界
```

**对策**：遇到不熟悉的 API，查官方文档确认。AI 说"这个 API 存在"不等于它存在。

### 2. 版本错配

```tsx
// 用 React 19 写法但在 React 18 项目里跑
<form action={submitAction}>   // 需要 React 19
```

**对策**：明确告诉它版本号，或者识别到它在用新语法时手动核对。

### 3. 过时写法（训练数据滞后）

| 它会写 | 应该用 |
|---|---|
| Vue 2 的 `this.$refs` | `ref` + `defineExpose` |
| class 组件 + `componentDidMount` | 函数组件 + `useEffect` |
| `axios` 到处散调 | TanStack Query / SWR |
| `moment.js` | `dayjs` / `date-fns` / `Temporal` |
| `node-sass` | `sass`（dart-sass） |
| webpack 配置 | Vite |

**对策**：项目里加 ESLint 规则，把废弃 API 挡在门禁上。

### 4. 看似合理但漏掉边界

```ts
// AI 常见产出
function average(list: number[]): number {
  return list.reduce((a, b) => a + b, 0) / list.length;
}
// 空数组 → NaN，没人处理
```

**对策**：凡是涉及除法、索引、`JSON.parse`、数组访问，都问一句"边界情况呢"。

### 5. 过度设计

让它写个工具函数，回来一个带策略模式、依赖注入、泛型约束的 80 行实现。

**对策**：明确约束"保持最小实现，不要引入设计模式"。

## 六、把 AI 产出纳入工程门禁

AI 生成的代码质量参差，**靠人眼不如靠门禁**。这也是为什么上一章（21-现代工程化）在 AI 时代更重要：

```bash
pnpm lint        # 风格与潜在错误
pnpm typecheck   # 类型错误（能挡住 40% 的幻觉 API）
pnpm test        # 行为正确性
pnpm build       # 构建期问题
```

**顺序有讲究**：`typecheck` 能抓到大量 AI 乱编的字段名和方法签名，成本极低，应该放在 review 之前跑。

### 针对 AI 的额外规则

```js
// eslint.config.js 补充
{
  rules: {
    // 禁止 any，AI 最爱用它逃避类型
    '@typescript-eslint/no-explicit-any': 'error',
    // 禁止未使用变量，AI 常留死代码
    '@typescript-eslint/no-unused-vars': 'error',
    // 禁止 eval / new Function
    'no-eval': 'error',
    'no-new-func': 'error',
    // 禁止直接 innerHTML（Vue/React 项目按需调整）
    'no-restricted-properties': ['error', {
      object: 'element',
      property: 'innerHTML',
      message: '存在 XSS 风险，请使用 textContent 或框架的安全 API'
    }],
  }
}
```

### PR 里标注 AI 参与程度

团队协作时建议约定：

- AI 生成后**自己完整读过并理解**才可以提交
- PR 描述里标注哪些部分是 AI 生成
- **你不理解的那行代码，不许合入**

## 七、提示词模板

几个直接能用的模板。

### 页面/组件生成

```
角色：资深前端工程师
技术栈：Vue 3 + TS + Vite + Pinia + Element Plus
上下文：@src/api/user.ts、@src/components/BaseTable.vue
任务：实现用户列表页
要求：
1. <script setup lang="ts">，类型完整，不用 any
2. 分页、搜索（防抖 300ms）、删除二次确认
3. loading 用骨架屏，空态用 ElEmpty
4. 请求走 @/api，不直接调 axios
5. 完成后列出：你用到的 API、可能的边界问题
```

### 代码审查

```
审查目标：@src/hooks/useUser.ts
检查项（按优先级）：
1. 竞态与取消（AbortController）
2. 依赖数组完整性
3. 内存泄漏（清理函数）
4. 错误处理与降级
5. 类型安全（any / 断言滥用）
输出：问题清单 + 行号 + 严重程度，不要重写代码。
```

### 重构

```
把以下 class 组件重构为函数组件 + Hooks：
@src/pages/OldPage.tsx
约束：
- 行为完全等价，不改业务逻辑
- 保留原有 props 接口
- useEffect 依赖要完整
- 输出 diff 而不是整文件
```

### Bug 定位

```
现象：点击删除后列表不刷新，但接口返回 200
技术栈：React 18 + TanStack Query
相关代码：@src/pages/UserList.tsx
请：
1. 列出 3 个最可能的原因（按概率排序）
2. 每个原因给出验证方法
3. 不要直接给我"改好的代码"，先定位
```

## 八、进阶：把 AI 接进工作流

### 1. MCP（Model Context Protocol）

MCP 让 AI 能**读写真实环境**，而不只是看你粘贴的文本。常见能力：

- 读项目文件、搜代码
- 跑命令、看测试结果
- 查数据库结构
- 调内部 API 文档

这样 AI 从"猜你的项目长什么样"变成"能看到你的项目"。

### 2. 后端类型 → 前端类型自动生成

```bash
# OpenAPI / Swagger 生成 TS 类型
pnpm dlx openapi-typescript ./openapi.json -o src/types/api.d.ts
```

配合 AI 用效果显著：**类型是准确的，AI 就不容易瞎编字段**。

### 3. 组件库文档 + AI

把组件库的文档站点作为上下文（或用 MCP 读取），让它生成符合你设计系统的代码，而不是套用网上的通用写法。

## 九、AI 时代什么能力更值钱了

工具改变后，能力权重也在变：

| 能力 | 变化 |
|---|---|
| **代码量产出速度** | ↓ 大幅贬值（AI 替代） |
| **需求判断与拆解** | ↑ 更值钱（AI 不会替你决定做什么） |
| **架构与边界划分** | ↑↑ 最值钱（AI 最弱的一环） |
| **调试与定位** | ↑ 更值钱（AI 给的方案需要验证） |
| **代码审查** | ↑↑ 更值钱（AI 产出需要人把关） |
| **领域业务理解** | ↑↑ 不可替代 |
| **读代码的能力** | ↑ 更重要（review AI 产出全在考这个） |

**结论**：AI 抬高了"表达"的效率，也就抬高了"判断"的相对价值。**基础越扎实，越能用好 AI**——因为你一眼能看出它哪里错了。这也是本教程前面所有章节（JS 语言核心、异步模型、浏览器原理）在 AI 时代反而更重要的原因。

## 十、小结

- AI 是**打字速度 + 候选生成器**，不是判断力。
- 上下文（技术栈、类型、已有代码）比提示词技巧重要得多。
- 小步生成、每步验证；错误会累积。
- 鉴权、金额、密钥、SQL、`innerHTML`、并发——必须逐行审 + 写测试。
- 常见错误模式：幻觉 API、版本错配、过时写法、漏边界、过度设计。
- 用 `lint + typecheck + test + build` 作为 AI 产出的门禁，把 `typecheck` 放最前面。
- **你不理解的那行代码不要合入。**
